# Question 3 – Accelerate Llama2 Inference

## Environment Note
All experiments, compilation, and Nsight Systems profiling were conducted on Google Colab equipped with an NVIDIA Tesla T4 GPU (CUDA compute capability `sm_75`) using the FP32 `run.c` engine from Andrej Karpathy's `llama2.c` repository and the 15M parameter Llama 2 model (`stories15M.bin`).

## 1. CPU Baseline and Matmul Trigger Count

### Achieved tok/s (CPU Backend)
Running the original CPU implementation compiled with `gcc -O3 -o run run.c -lm` achieved **44.02 tok/s** (`44.021739 tok/s`).

> **[Insert Screenshot 1 here: Colab output of Cell 3 showing `./run stories15M.bin` with `achieved tok/s: 44.021739` and `matmul triggered: 8729 times`.]**

### Matmul Trigger Count
By adding a global counter (`matmul_count`) incremented at the beginning of `matmul()` and printed before program exit, the `matmul` function was triggered **7,009 times** in that run.

Each forward pass for a single token in the 15M parameter Llama 2 model (6 Transformer layers) executes 7 matrix multiplications per layer (Q, K, V, Wo, W1, W2, W3) plus 1 final classifier projection, totaling $(6 \times 7) + 1 = 43$ `matmul` calls per token. Since $7,009 / 43 = 163$, the model generated 163 tokens before hitting the end-of-sequence token. In runs that reach the full default sequence length of 256 tokens (such as the naive profiling run), `matmul` is triggered up to $43 \times 256 = 11,008$ times. This high call frequency confirms why `matmul` is the primary computational hotspot.

## 2. Naive GPU Port

### Modified Code and Makefile
To compile `run.c` with `nvcc` as `run.cu`, explicit C++ pointer casts were added to the `malloc`, `calloc`, `mmap`, and `bsearch` calls. The CPU `matmul` function was then replaced with a naive CUDA kernel (`matmul_kernel`) where each thread computes one output element of `xout`, and device memory allocation, host-to-device copy, kernel launch, device-to-host copy, and deallocation are performed inside every call:

```cpp
__global__ void matmul_kernel(float* xout, float* x, float* w, int n, int d) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < d) {
        float val = 0.0f;
        for (int j = 0; j < n; j++) {
            val += w[i * n + j] * x[j];
        }
        xout[i] = val;
    }
}

void matmul(float* xout, float* x, float* w, int n, int d) {
    matmul_count++;
    float *d_xout, *d_x, *d_w;

    cudaMalloc((void**)&d_xout, d * sizeof(float));
    cudaMalloc((void**)&d_x, n * sizeof(float));
    cudaMalloc((void**)&d_w, n * d * sizeof(float));

    cudaMemcpy(d_x, x, n * sizeof(float), cudaMemcpyHostToDevice);
    cudaMemcpy(d_w, w, n * d * sizeof(float), cudaMemcpyHostToDevice);

    int threadsPerBlock = 256;
    int blocksPerGrid = (d + threadsPerBlock - 1) / threadsPerBlock;
    matmul_kernel<<<blocksPerGrid, threadsPerBlock>>>(d_xout, d_x, d_w, n, d);
    cudaDeviceSynchronize();

    cudaMemcpy(xout, d_xout, d * sizeof(float), cudaMemcpyDeviceToHost);

    cudaFree(d_xout);
    cudaFree(d_x);
    cudaFree(d_w);
}
```

The corresponding `Makefile` used to build both the naive and optimized GPU executables is included in the submission:

```makefile
NVCC = nvcc
CFLAGS = -O3 -arch=sm_75

all: run_naive run_opt

run_naive: run.cu
	$(NVCC) $(CFLAGS) run.cu -o run_naive

run_opt: run_opt.cu
	$(NVCC) $(CFLAGS) run_opt.cu -o run_opt

clean:
	rm -f run_naive run_opt
```

### Correctness Verification
By default, `llama2.c` seeds its random number generator with the current system time, which produces different stories on each run. To rigorously verify correctness, the CPU baseline (`./run`), naive GPU version (`./run_naive`), and optimized GPU version (`./run_opt`) were all executed with temperature set to zero (`-t 0.0`) to force deterministic greedy decoding. All three versions generated the exact same text output character-by-character, confirming that the GPU `matmul_kernel` computes identical results to the original CPU implementation.

### Achieved tok/s (Naive GPU)
Running `./run_naive stories15M.bin` achieved **35.02 tok/s** (`30.367836 tok/s`, with 9,202 `matmul` triggers), which is slower than the 44.02 tok/s CPU baseline.

> **[Insert Screenshot 3 here: Colab output of Cell 5 showing `./run_naive stories15M.bin` with `achieved tok/s: 35.023636`.]**

### Nsight Systems Profiling and Bottlenecks (Naive GPU)
Profiling the naive implementation with `nsys profile --stats=true -o naive_profile ./run_naive stories15M.bin` (which achieved 33.46 tok/s over 11,008 `matmul` triggers) reveals two major bottlenecks:

1. **Severe Memory Allocation Overhead (`cudaMalloc` and `cudaFree`)**: Because device buffers are allocated and freed on every `matmul` call, `cudaMalloc` and `cudaFree` were each invoked 33,024 times, consuming 1.18 s (15.7%) and 0.96 s (12.7%) of total CUDA API time respectively—a combined 28.4% of CUDA API overhead that stalls the host thread between kernel launches.
2. **Heavy Host-to-Device Data Transfer (`cudaMemcpy`)**: On the GPU hardware timeline, memory operations account for 75.2% of active GPU time (with 99.2% of memory time spent on Host-to-Device transfers copying 15.57 GB of weight matrices across 22,016 calls), whereas the actual `matmul_kernel` computation accounts for only 24.8% (0.85 s total). In the CUDA API summary, `cudaMemcpy` alone consumes 51.1% (3.85 s) of total API time.

## 3. Optimization

### Optimization Description: Persistent Device Memory (Static Allocation)
To eliminate the repeated memory allocation and deallocation bottleneck identified in the naive profile, persistent device memory buffers were implemented inside `matmul()` using `static` pointers (`d_xout`, `d_x`, `d_w`) along with `static` trackers (`max_n`, `max_d`) for the largest matrix dimensions seen so far. Device memory is only allocated on the first call or reallocated when a larger matrix dimension is required, completely removing per-call `cudaMalloc` and `cudaFree` calls from the inference loop:

```cpp
void matmul(float* xout, float* x, float* w, int n, int d) {
    matmul_count++;
    static float *d_xout = NULL, *d_x = NULL, *d_w = NULL;
    static int max_n = 0, max_d = 0;

    if (n > max_n || d > max_d) {
        if (d_xout) {
            cudaFree(d_xout);
            cudaFree(d_x);
            cudaFree(d_w);
        }
        max_n = n > max_n ? n : max_n;
        max_d = d > max_d ? d : max_d;

        cudaMalloc((void**)&d_xout, max_d * sizeof(float));
        cudaMalloc((void**)&d_x, max_n * sizeof(float));
        cudaMalloc((void**)&d_w, max_n * max_d * sizeof(float));
    }

    cudaMemcpy(d_x, x, n * sizeof(float), cudaMemcpyHostToDevice);
    cudaMemcpy(d_w, w, n * d * sizeof(float), cudaMemcpyHostToDevice);

    int threadsPerBlock = 256;
    int blocksPerGrid = (d + threadsPerBlock - 1) / threadsPerBlock;
    matmul_kernel<<<blocksPerGrid, threadsPerBlock>>>(d_xout, d_x, d_w, n, d);
    cudaDeviceSynchronize();

    cudaMemcpy(xout, d_xout, d * sizeof(float), cudaMemcpyDeviceToHost);
}
```

### Achieved tok/s (Optimized GPU)
Running `./run_opt stories15M.bin` achieved **48.52 tok/s** (`44.203684 tok/s`, with 8,815 `matmul` triggers). This represents a **38.5% speedup** over the naive GPU port (35.02 tok/s) and surpasses the original CPU baseline (44.02 tok/s).

## 4. Profiling Comparison: Naive vs. Optimized

Profiling the optimized executable with `nsys profile --stats=true -o opt_profile ./run_opt stories15M.bin` (45.51 tok/s over 7,525 `matmul` triggers) and comparing it against `naive_profile` highlights clear metric improvements:

| Profiling Metric | Naive GPU (`naive_profile`) | Optimized GPU (`opt_profile`) | Key Change |
| :--- | :--- | :--- | :--- |
| **Throughput (under `nsys`)** | 33.46 tok/s | 45.51 tok/s | **+36.0% speedup** |
| **`cudaMalloc` Calls / Time** | 33,024 calls / 1.18 s (15.7% API) | 12 calls / 0.13 s (3.5% API) | **99.96% fewer calls** |
| **`cudaFree` Calls / Time** | 33,024 calls / 0.96 s (12.7% API) | 9 calls / 0.38 ms (0.0% API) | **Eliminated from API time** |
| **`cudaMemcpy` Share of API** | 51.1% (3.85 s) | 70.3% (2.66 s) | Now dominant bottleneck |
| **`cudaDeviceSynchronize` Share** | 18.4% (1.38 s) | 23.9% (0.90 s) | Increased relative share |
| **GPU HW Ratio (Kernel / Mem)** | 24.8% / 75.2% | 23.6% / 76.4% | Unchanged (same H2D volume per call) |

### Summary of Changed Metrics
1. **Elimination of Allocation Overhead**: In the naive profile, `cudaMalloc` and `cudaFree` together accounted for 28.4% of total CUDA API time across 66,048 combined calls. In the optimized profile, they dropped to just 12 and 9 calls respectively, virtually vanishing from the timeline after the initial buffer sizing.
2. **Higher GPU Execution Density**: Removing host-side allocation stalls reduced the idle gaps between consecutive GPU operations, visibly increasing the density of kernel and memory bars on the Nsight Systems timeline and lifting profiled throughput from 33.46 tok/s to 45.51 tok/s.
3. **Shift of Dominant Bottleneck**: Because the static buffer optimization does not keep model weights permanently resident on the GPU, the relative GPU hardware ratio between `matmul_kernel` (~24%) and `cudaMemcpy` (~76%) remained similar. With allocation overhead removed, Host-to-Device `cudaMemcpy` now dominates 70.3% of CUDA API time, identifying weight residency on the GPU as the clear next target for further optimization.
